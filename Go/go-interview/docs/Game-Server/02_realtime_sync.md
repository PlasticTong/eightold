# 网络同步、延迟与反作弊

## 1. 两种主流同步方式

| 模型 | 服务端负责什么 | 典型适用 | 主要代价 |
| --- | --- | --- | --- |
| 状态同步 | 维护权威世界、下发快照 | RPG、FPS、MMO、动作游戏 | 服务端算力和带宽较高 |
| 帧同步 | 收集/转发每帧操作 | 棋牌游戏、策略、部分 MOBA | 要求客户端逻辑确定，作弊治理更难 |

### 状态同步

```text
客户端输入 ──→ 服务端校验与模拟 ──→ 状态快照 ──→ 所有客户端
```

客户端为降低“按键到反馈”的等待感，可先做本地预测；收到权威快照后，比对并平滑校正。其他玩家通常渲染稍早的两个快照之间的位置，这叫**插值**，能遮住网络到达时间不均匀造成的抖动。

### 帧同步

```text
客户端操作 ──→ 服务端收集/排序 ──→ 本帧操作集 ──→ 所有客户端按同一规则执行
```

帧同步传输量小、回放自然，但需要固定时间步长、确定的随机数、统一的浮点/物理策略，以及掉帧与重连方案。不要把它简单理解成“服务端不用做事”。

## 2. 输入包应包含什么

不要上报绝对位置和结果。输入包可设计为：

```text
matchID | playerID | clientTick | sequence | command | parameters
```

- `sequence` 用来去重、检测乱序和丢包；
- `clientTick` 只作为参考，不能盲信；
- 服务端要检查频率、合法范围、资源/CD、视野和房间归属；
- 结果必须由服务端计算并赋予服务端序号。

## 3. 反作弊从边界开始

| 不可信输入 | 服务端验证 |
| --- | --- |
| 位置/速度 | 最大速度、碰撞、寻路、时间差 |
| 攻击/技能 | CD、蓝量、距离、目标状态、伤害公式 |
| 金币/掉落 | 只接受行为，不接受最终数值 |
| 匹配结果 | 由匹配服务签发短期令牌 |

“服务端权威”不等于绝对无挂，但它把关键规则从客户端移到可控边界。外挂仍可能通过自动操作、视觉识别、协议重放影响体验，因此还需频率限制、行为审计、封禁和回放证据。

## 4. 可靠性与体验的取舍

- **TCP/WebSocket**：顺序可靠，适合登录、聊天、回合制和多数轻量实时游戏；但丢包可能阻塞后续数据。
- **UDP/QUIC 类方案**：适合高频位置和射击输入；应用层要处理序号、选择性可靠和拥塞控制。
- **不要每次状态都可靠发送**：位置快照过期后通常没有价值，优先发最新快照。
- **心跳不是业务包**：用于探测连接与测量 RTT；离线判定应留出网络抖动余量。

## 5. 一份可操作的同步检查表

1. 每个输入是否有序号、限频、鉴权和房间校验？
2. 服务器是否是关键状态的唯一权威来源？
3. 快照是否区分全量基线与增量更新？
4. 客户端是否能处理乱序、重复、过期快照？
5. 断线重连是否拿到可靠的当前状态，而不是复用旧缓存？
