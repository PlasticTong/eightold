# 面试题与线上排障

## 高频问题

### 1. 为什么游戏服常说“服务端权威”？

客户端处于玩家设备上，输入、内存和协议都可能被篡改。服务端权威的含义是：客户端提交操作意图，服务端校验并计算关键结果，客户端只是展示或预测。它能减少改数值、瞬移、伪造伤害等作弊面。

### 2. 状态同步和帧同步怎么选？

看游戏类型与信任边界。强对抗、物理复杂、玩家多的场景更常用状态同步；规则离散、可保证确定性、希望低服务端模拟成本的场景可考虑帧同步。很多游戏也会混用：战斗走实时同步，聊天、背包和商城走普通业务协议。

### 3. 为什么一个房间建议单线程更新？

它不是为了“性能更高”，而是为了让状态变化有明确顺序。网络读写可以并发；战斗规则由同一个房间循环执行，可避免多 goroutine 抢改血量、位置、Buff 导致的竞态与不一致。

### 4. 如何处理掉线重连？

断线时先标记会话不可用但保留短暂的玩家/房间状态；重连通过短期令牌验证身份和房间归属；下发一个可靠基线快照，再接收增量同步。不要只凭 playerID 直接“顶号”。

### 5. 如何防止重复结算？

每局生成全局唯一 `matchID`，按 `matchID + playerID + rewardType` 写入具备唯一约束的奖励记录；业务更新和事件投递采用事务或可靠事件表。消费失败允许重试，但同一业务键只能成功一次。

## 排障：房间 Tick 偶尔超过 50ms

按以下顺序看：

1. **确认范围**：是单个房间、某个地图、某台机器还是全局？
2. **看指标**：Tick P50/P95/P99、goroutine 数、GC pause、CPU、收包队列、在线人数。
3. **抓证据**：CPU/trace 看是否计算过重；goroutine profile 看是否锁竞争、网络阻塞或 channel 堵塞。
4. **找根因**：常见是 Tick 内做了数据库/HTTP 调用、全量广播过大、慢客户端阻塞写入、频繁分配触发 GC、某技能算法复杂度失控。
5. **修复和回归**：把 I/O 移到异步边界，限制每 Tick 工作量，做差量广播，加入压测场景与告警阈值。

## 排障：在线人数增加后延迟突然变高

不要只看平均值。先分“客户端网络 RTT 上升”和“服务端处理排队”两类：

- RTT 稳定而消息处理延迟升高：重点查网关/房间队列、CPU、GC、锁竞争；
- 某区域 RTT 整体升高：检查节点地域、网络质量、跨区调度；
- 只有少数用户异常：检查弱网、丢包、设备性能与慢连接策略。

关键指标应有：连接数、在线房间数、每秒入/出包、队列长度、房间 Tick 耗时、快照大小、丢包/重传、Redis/MySQL 延迟和错误率。
