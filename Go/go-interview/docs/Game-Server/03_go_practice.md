# Go 实战路线：从聊天室到房间战斗服

## 项目 1：带心跳的 WebSocket 聊天室

目标：理解连接生命周期。

- `Hub` 管理注册、注销、广播；
- 每个连接有读循环和写循环，写入通过有界 channel；
- ping/pong 检测死连接；
- 慢客户端不能无限积压消息：队列满时断开或丢弃低优先级消息。

验收：100 个并发客户端可连接、广播、断开；`go test -race` 无竞态。

## 项目 2：房间与匹配

目标：理解“一个房间一个状态机”。

```text
JoinQueue → Matchmaker → RoomManager → Room.Run()
```

- 匹配队列使用 `context` 支持取消；
- `RoomManager` 按 `roomID` 定位房间；
- `Room.Run` 是唯一修改战局状态的 goroutine；
- 房间结束产生 `matchID`，异步投递结算事件。

验收：能创建 1v1 房间、超时关闭房间、重复结算不会重复发奖励。

## 项目 3：状态同步的 2D 小游戏

目标：理解 Tick、快照与延迟。

- 服务端 20 Tick/s 更新位置；
- 客户端每次只发送方向/操作序号；
- 服务端 10 次/s 发快照；
- 客户端保存最近快照并插值渲染；
- 人为注入 100ms 延迟、随机丢包，观察抖动和校正。

验收：故意把客户端速度改成 10 倍，服务端仍拒绝非法移动。

## 项目 4：大厅业务

目标：把常规 Go 后端能力接到游戏场景。

| 模块 | 设计重点 |
| --- | --- |
| 背包 | 物品变更流水、事务、唯一请求 ID |
| 排行榜 | Redis ZSET、定期落库、赛季结算 |
| 邮件 | 异步投递、附件领取幂等 |
| 结算 | matchID 幂等、失败重试、审计日志 |

## 必备工程工具

- 用 `pprof` 看 CPU、堆和 goroutine 堆积；
- 用 `go test -race` 找共享状态竞态；
- 用压测模拟连接数、房间数、消息频率与慢客户端；
- 用 Prometheus 监控在线人数、房间 Tick 耗时、收发包、队列长度、GC、错误率；
- 日志里至少带 `playerID`、`roomID`、`matchID` 与请求序号。

## 选择框架的建议

先手写一版最小房间服，了解边界后再评估 [Nakama](https://heroiclabs.com/docs/nakama/) 或 [Pitaya](https://github.com/topfreegames/pitaya)。框架能减少通用设施工作，但不能替你确定游戏规则、同步策略和业务一致性。
