# 架构与服务拆分

## 1. 一局游戏的最小闭环

一个可对战的房间至少有四类职责：

```text
收输入 → 校验输入 → 推进世界 → 广播结果
```

例如玩家点击“攻击”：服务端先验证玩家是否在这个房间、是否存活、CD 是否结束、目标是否可见；通过后才改变战斗状态，并广播事件或快照。这样即使客户端被篡改，也不能直接改伤害或金币。

## 2. 常见服务拆分

| 服务 | 职责 | 状态特点 |
| --- | --- | --- |
| 网关 | 连接、协议编解码、鉴权、限流、路由 | 连接状态，可快速替换 |
| 登录/大厅 | 账号、好友、背包、邮件、活动 | 持久业务数据 |
| 匹配 | 入队、规则筛选、组队、选区 | 短暂队列状态 |
| 房间/战斗 | Tick、游戏规则、同步、结算 | 一局内存态，单写者优先 |
| 数据服务 | MySQL、Redis、对象存储、消息队列 | 长期数据与异步任务 |

小项目不必一开始拆成微服务：一个进程里按模块划分即可。只有在连接数、战斗算力、发布频率明显不同后，才按边界拆进程。

## 3. 房间模型：单写者优先

最容易写错的做法，是让多个 goroutine 随时直接改同一个 `Room`。更稳妥的模型是：

```text
网络 goroutine 把输入放入 room.inbox
                       ↓
            房间主循环按 Tick 顺序处理
                       ↓
         只由主循环修改游戏世界与生成广播
```

这不是说完全不用并发；网络 I/O、日志和存储可以并发。但**同一局的核心状态**应该有一个明确写入序列，能显著降低竞态和偶发状态错乱。

```go
type Room struct {
    inbox chan Input
    state World
}

func (r *Room) Run(ctx context.Context) {
    ticker := time.NewTicker(50 * time.Millisecond) // 20 Tick/s
    defer ticker.Stop()
    for {
        select {
        case in := <-r.inbox:
            r.state.ApplyIfValid(in)
        case <-ticker.C:
            r.state.Step()
            r.BroadcastSnapshot()
        case <-ctx.Done():
            return
        }
    }
}
```

示例是教学简化版：生产中还要限制单 Tick 处理量、处理 inbox 堆积、记录输入序号，并把慢客户端踢出或降频。

## 4. 匹配与分配

匹配不能只按“第一个进来先配”。常见排序维度有：模式、段位差、组队人数、地区、预计 RTT、等待时长。

实务上通常会逐步放宽规则：等待 5 秒只接受相近段位，等待越久允许的段位差越大。匹配成功后创建或分配房间，再返回给客户端连接所需的地址、端口和令牌。

## 5. 结算为什么要幂等

结算网络超时后，客户端或消息消费者可能重试。如果“加金币、发奖励、写战绩”不是幂等的，重试就会重复发奖。

可使用 `matchID + playerID + rewardType` 作为唯一业务键；数据库唯一索引或事务保证“同一局同一奖励最多生效一次”。
