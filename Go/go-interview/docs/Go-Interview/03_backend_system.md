# Go 后端场景题：从语言到线上系统

## 1. 请求突然变慢，如何排查？

**先定边界和量化指标，再分层定位，不要第一时间改代码或扩容。**

```text
告警 / 用户反馈
→ QPS、错误率、P50/P95/P99、CPU、RSS、GC、goroutine
→ 网关 / 应用 / DB / Redis / MQ / 下游
→ 定位瓶颈
→ 降级止血、修复、复盘
```

- 先比较“慢的是全部请求还是某接口/某机房/某版本”。
- Go 服务重点看：goroutine 堆积、锁竞争、GC pause/CPU、连接池等待、下游超时。
- 用 trace 把单请求拆成等待和执行时间；用 CPU/heap/goroutine profile 验证假设。

## 2. 如何设计超时、重试和熔断？

**超时是边界，重试是受控补偿，熔断是保护系统；三者不能各自无限叠加。**

- 请求入口设总 deadline，再把剩余时间传递给下游；不要每层各自给一个完整 3 秒。
- 只重试幂等操作或有幂等键的操作；限制次数并使用退避与抖动。
- 错误率高、延迟升高时快速失败或降级，给依赖恢复时间。
- 必须记录超时原因、依赖名和剩余 deadline，否则复盘无法判断是本服务慢还是下游慢。

## 3. 如何保证接口幂等？

**用业务唯一键把“同一业务动作”归并，并让重复请求返回同一结果或安全失败。**

常见实现：客户端请求 ID + 数据库唯一索引；状态机条件更新；消息消费端记录去重键；支付/扣库存使用业务流水号。仅靠 Redis 锁不能单独保证最终幂等，因为锁会过期、进程会崩溃。

## 4. 高并发扣库存怎么做？

**先确定一致性目标，再选择数据库条件更新、乐观锁、队列串行化或预扣库存；任何方案都要覆盖重复请求与失败补偿。**

数据库基础写法：

```sql
UPDATE stock
SET available = available - :n
WHERE sku_id = :sku AND available >= :n;
```

检查受影响行数；订单创建、扣减、支付回调需要状态机和幂等键。库存极热点时可按 SKU 分片、预热、排队或限流，但不能把“缓存扣成功”当最终事实。

## 5. Redis 缓存与数据库如何保持一致？

**缓存通常不是事实来源；优先明确读写路径，并接受可量化的短暂不一致。**

- 常用 cache-aside：读未命中查库回填；写先更新库，再删除缓存。
- 删除失败要有重试或订阅 binlog 的补偿；热点 key 要处理击穿，空值/布隆过滤器可防穿透。
- 先定义数据可见延迟与可接受错误，再讨论双删、延迟删除等技巧。

## 6. 消息如何做到“至少一次”下不重复处理？

**消息系统常提供至少一次投递，消费者必须幂等；不要承诺绝对“只消费一次”。**

- 消费处理和去重记录/业务状态一起落库，利用唯一约束或条件更新。
- 先处理业务还是先提交 offset 取决于系统能力，但必须考虑两步之间进程崩溃。
- 失败重试要有上限、死信队列、告警和人工处理入口。

## 7. HTTP Client 为什么会拖垮服务？

**未设置超时、未关闭响应体、错误复用连接或无限并发下游请求，都可能造成连接与 goroutine 堆积。**

- 复用长生命周期的 `http.Client` 和合理配置的 `Transport`。
- 每次响应都及时 `resp.Body.Close()`；读取策略与连接复用需求一致。
- 通过 context 传递 deadline；为下游设置并发上限和队列长度。

## 8. 项目题怎么讲才有说服力？

**讲清你的决策，而不只报技术名词：问题、约束、方案、指标、结果、遗留风险。**

```text
业务目标：把什么指标改善到什么程度
约束：成本、数据一致性、上线窗口、已有系统
方案：为什么不用另外两个方案
验证：压测、灰度、监控指标
结果：真实数据
复盘：仍有的风险与下一步
```

如果没有精确数字，明确说“当时没有埋点，下一次会补哪几个指标”，不要编造。
